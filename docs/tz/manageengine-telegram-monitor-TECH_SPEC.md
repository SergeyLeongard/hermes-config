# Техническое задание

## Проект: Telegram-бот первой линии для ManageEngine ServiceDesk Plus

**Рабочее название:** `manageengine-telegram-monitor`
**Роль:** SDP Bot, диспетчер заявок IT
**Канал:** Telegram-группа техподдержки
**Интеграция:** ManageEngine ServiceDesk Plus API
**Платформа:** Hermes Agent + Hermes Gateway
**Среда:** Ubuntu Server `s-hermes-agent`, IP `10.251.0.192`
**Текущий инстанс SDP:** `http://s-sd.shin-line.com/`
**Основная цель:** автоматизировать первичный прием обращений пользователей из Telegram и создавать/вести заявки в ManageEngine SDP.

---

# 1. Цель проекта

Создать Telegram-бота первой линии IT-поддержки, который:

1. читает сообщения пользователей в Telegram-группе;
2. отличает реальные IT-проблемы от мусора, приветствий и служебных сообщений;
3. создает заявки в ManageEngine ServiceDesk Plus;
4. добавляет последующие сообщения пользователя в уже созданную заявку как note/комментарий;
5. не плодит дубли;
6. хранит локальный контекст обращения;
7. в будущем сможет анализировать историческую базу заявок, искать похожие проблемы и предлагать решения до создания новой заявки.

# 3. Общая архитектура

С 2026-05-11 используется раздельная двухконтурная архитектура:

```text
Контур A (Production incidents)
Пользователь Telegram (боeвая группа, тема Инциденты)
        ↓
HermesIncidentAssit_Bot (dispatcher-only)
        ↓
manageengine-telegram-monitor/dispatcher_bot.py
        ↓
process_message() / context.json / антидубли
        ↓
ManageEngine SDP API
        ↓
Шаблонный ответ в тему Инциденты

Контур B (Operations / control)
Админ-пользователи Telegram (группа ТестИттехпод)
        ↓
HermesSD.bot (Hermes Gateway)
        ↓
Управление, отладка, конфигурация, развитие проекта
```

Критично: production-контур диспетчера не использует ad-hoc terminal/python команды и не выполняет текст пользователя как команду.

# 5. Роль и поведение бота

Бот — это **не разговорный ассистент**, а диспетчер заявок.

Он не должен:

1. вести свободную переписку;
2. отвечать на приветствия;
3. благодарить;
4. спорить;
5. писать длинные объяснения;
6. использовать эмодзи;
7. отвечать на сообщения сотрудников IT-поддержки;
8. раскрывать токены, ключи, внутренние ошибки API пользователям.

Он должен отвечать строго по шаблону:

```text
Заявка №4021 создана
👤 Пользователь: <name> (ID: <telegram_user_id>)
📝 Тема: <subject>
🏷 Категория: <name> (<id>)
🆔 UDF поле (IDUserTelegram): @<telegram_username>

Добавлено к заявке №4021
С каким ПО или оборудованием проблема?
Опишите проблему текстом, пожалуйста.
```

One-line формат `Заявка №<id> создана. Категория: ...` запрещен.

# 6. Telegram-контур

## 6.1 Группы и маршрутизация

Production incidents (диспетчер):

```env
DISPATCHER_TARGET_CHAT_ID=-1003568410359
DISPATCHER_TARGET_TOPIC_ID=3
DISPATCHER_BOT_USERNAME=@HermesIncidentAssit_Bot
```

Control/operations (Hermes):

```env
HERMES_CONTROL_CHAT_ID=-1003990457960
HERMES_BOT_USERNAME=@HermesSDS001bot
```

Правило маршрутизации:
1. `HermesIncidentAssit_Bot` слушает только `DISPATCHER_TARGET_CHAT_ID` и только тему `DISPATCHER_TARGET_TOPIC_ID`.
2. `HermesSD.bot` остается в `HERMES_CONTROL_CHAT_ID` как управляющий бот.
3. Диспетчер не должен отвечать вне темы инцидентов.

## 6.2 Доступ

Текущая идея:

```text
диспетчер обрабатывает сообщения всех участников целевой темы, кроме сотрудников IT-поддержки
```

## 6.3 Группа исполнителей в SDP

При создании каждого инцидента бот обязан назначать группу исполнителей "IT поддержка".

Реализация через env:

```env
MANAGEENGINE_DEFAULT_GROUP=IT поддержка
# при наличии надежного ID группы использовать приоритетно:
# MANAGEENGINE_DEFAULT_GROUP_ID=<group_id>
```

Правило приоритета:
1. если задан `MANAGEENGINE_DEFAULT_GROUP_ID` — отправлять `request.group.id`;
2. иначе если задан `MANAGEENGINE_DEFAULT_GROUP` — отправлять `request.group.name`;
3. если оба не заданы — это ошибка конфигурации для production-контура.

Для этого нужна переменная:

```env
TELEGRAM_SUPPORT_STAFF_IDS=
```

Пример:

```env
TELEGRAM_SUPPORT_STAFF_IDS=111111111,222222222,333333333
```

Сообщения от этих пользователей полностью игнорируются.

# 7. Фильтрация сообщений

## 7.1 Полностью игнорировать

Бот ничего не отвечает и не создает заявку, если сообщение:

1. от пользователя из `TELEGRAM_SUPPORT_STAFF_IDS`;
2. является приветствием:

```text
привет
здравствуйте
добрый день
hi
hello
салам
```

3. является оффтопом, шуткой, болтовней;
4. является Telegram service message:

```text
join
left
pinned
new_chat_member
```

5. является slash-командой:

```text
/start
/help
/new
/done
/status
```

На текущем этапе команды отключены.

6. является дублем того же текста от того же пользователя за последние 2 минуты;
7. содержит только фото/файл без текста и нет активного контекста;
8. является voice-сообщением на текущем этапе.

## 7.2 Обрабатывать

Бот должен обрабатывать:

1. IT-проблемы;
2. ошибки и сбои;
3. запросы доступа;
4. проблемы с 1С/ERP;
5. проблемы с интернетом/сетью/VPN/Wi-Fi;
6. проблемы с почтой;
7. проблемы с принтерами;
8. проблемы с ПК/ноутбуками/мониторами;
9. дополнения к активной заявке;
10. сообщения с недостаточной конкретикой.

# 10. Неясная проблема

Если сообщение похоже на IT-проблему, но непонятно, что именно сломалось, бот задает один короткий вопрос:

```text
Опишите проблему подробнее: что именно не работает: сеть, 1С, почта, доступ или оборудование?
```

Пример:

```text
Пользователь: У меня не работает
Бот: Опишите проблему подробнее: что именно не работает: сеть, 1С, почта, доступ или оборудование?
```

После ответа пользователя бот должен создать заявку.

# 11. Новая категория

Если появляется проблема, которой нет в словаре категорий:

1. заявку создавать в `Прочее`;
2. в description добавлять:

```text
Возможна новая категория: <краткое описание>
```

3. логировать событие в `monitor.log`;
4. не создавать новые категории в ManageEngine автоматически.

# 13. Логика контекста

Контекст хранится по пользователю, но обновление заявки выполняется не по факту
"тот же пользователь", а по совпадению темы:

```text
context_key = telegram_user_id
match_key = topic_signature(message)
```

TTL активного контекста:

```env
CONTEXT_TTL_MINUTES=60
```

## 13.1 Создать новую заявку, если

1. у пользователя нет активного контекста;
2. прошло больше 60 минут с последнего сообщения;
3. пользователь явно пишет:

```text
новая заявка
другая проблема
еще проблема
ещё одна проблема
теперь другая проблема
```

4. категория изменилась;
5. бот определил смену темы;
6. нет похожей активной заявки по score (см. 13.4).

## 13.2 Добавить note к существующей заявке, если

1. у пользователя есть активный контекст;
2. TTL не истек;
3. тема не изменилась;
4. есть match с одной из активных заявок пользователя (см. 13.4).

Пример:

```text
Пользователь: Не работает интернет на втором этаже
Бот: Заявка №4021 создана. Категория: Сеть

Пользователь: Еще DNS ошибку пишет
Бот: Добавлено к заявке №4021
```

## 13.3 Очистка контекста

Раз в час удалять записи старше 2 часов.

```env
CLEANUP_INTERVAL_MINUTES=60
```

## 13.4 Анти-склейка по score

Для каждого нового IT-сообщения рассчитывать score совпадения с каждой активной
заявкой пользователя (0..1):

1. текстовое сходство с последним сообщением в заявке;
2. совпадение системных маркеров (`outlook`, `vpn`, `rds`, `1c`, `wms`, `flux` и т.д.);
3. временной штраф (чем старее активная заявка, тем ниже score).

Пороговые действия:

1. `score >= 0.78` -> добавить note в найденную заявку;
2. `0.45 <= score < 0.78` -> запросить короткое уточнение (эта же заявка или новая);
3. `score < 0.45` -> создать новую заявку.

Явные маркеры новой темы всегда форсируют новую заявку:

```text
другая проблема
еще один вопрос
кстати еще
новая заявка
```

Пример:

```text
1) Пользователь: "не работает мышь" -> создана заявка №7001
2) Пользователь: "и еще не открывается rdp" -> низкий score к №7001 -> новая заявка №7002
3) Пользователь: "мышь совсем умерла" -> высокий score к №7001 -> note в №7001
```

# 14. Антидубли

Если тот же пользователь отправил идентичный текст в течение 2 минут:

1. не создавать заявку;
2. не добавлять note;
3. не отвечать.

Параметр:

```env
DUPLICATE_WINDOW_SECONDS=120
```

---

# 15. Антиспам

Если пользователь отправил больше 5 сообщений за 1 минуту:

1. первые 5 сообщений обрабатываются;
2. 6-е и следующие временно игнорируются;
3. один раз за окно спама бот отвечает:

```text
Слишком много сообщений. Подождите реакции инженера.
```

Параметр:

```env
SPAM_THRESHOLD_PER_MINUTE=5
```

# 16. Создание заявки в ManageEngine SDP

Endpoint:

```text
POST {SDP_BASE_URL}/api/v3/requests
```

Формат передачи:

```text
Content-Type: application/x-www-form-urlencoded
Поле: input_data=<json string>
Заголовок: Authtoken: <SDP_API_TOKEN>
```

Пример логической структуры `input_data`:

```json
{
  "request": {
    "subject": "[Сеть] Не работает интернет на втором этаже",
    "description": "Источник: Telegram\nChat ID: -1001234567890\nTelegram user_id: 669079966\nUsername: @username\nВремя: 2026-05-07 12:30\n\nСообщение:\nНе работает интернет на втором этаже",
    "requester": {
      "id": "1011"
    },
    "category": {
      "id": "605"
    },
    "priority": {
      "name": "Normal"
    },
    "template": {
      "id": "1"
    },
    "udf_fields": {
      "udf_sline_301": "669079966"
    }
  }
}
```

Важно: по результатам тестов requester через `id` работает надежнее, чем `email_id`.

# 17. Subject

Требования:

1. максимум 100 символов;
2. формат:

```text
[Категория] Краткое описание
```

Примеры:

```text
[Сеть] Не работает интернет на втором этаже
[ERP] Не открывается 1С
[Принтера] Принтер не печатает в бухгалтерии
[Доступ] Не получается войти в учетную запись
```

Если текст длинный — обрезать до 100 символов без потери смысла.

# 34. MVP — минимально рабочая версия

MVP должен делать только это:

1. принять текст из Telegram-группы;
2. проверить, что отправитель не IT-сотрудник;
3. не использовать расширенные pre-gate/pre-filter словари;
4. определить категорию по ключам;
5. определить приоритет по ключам;
6. создать заявку в ManageEngine;
7. сохранить контекст;
8. ответить номером заявки;
9. следующие сообщения пользователя добавлять как note;
10. не создавать дубли.

# 35. Критерии готовности MVP

MVP считается готовым, если:

1. бот стабильно отвечает в тестовой Telegram-группе;
2. сообщения от IT-сотрудников игнорируются;
3. приветствия игнорируются;
4. текст `Не работает интернет` создает заявку в SDP;
5. текст `Еще DNS ошибка` добавляется как note к той же заявке;
6. текст `Еще принтер не печатает` создает новую заявку;
7. дубль сообщения за 2 минуты игнорируется;
8. при падении SDP сообщение попадает в `pending_messages.json`;
9. токены не попадают в логи;
10. после перезапуска Hermes контекст не теряется.

## 35.1 Критерии выхода из теста в боевой чат

Перед добавлением бота в реальный чат минимум 3 дня теста в тестовой группе.

Минимальные метрики:

1. не менее 100 входящих сообщений за период;
2. false merge rate (ложная склейка разных тем) < 5%;
3. false non-IT rate (IT ошибочно отклонен) < 3%;
4. no critical incidents: массовая некорректная маршрутизация или спам-ответы.

Если метрики не выполнены, прод-подключение откладывается до следующей итерации
настройки порогов и prompt.

## 35.2 Пограничные IT-сообщения (triage)

Классификатор должен возвращать одно из трех состояний:

1. `IT` -> create/update по правилам контекста;
2. `NON_IT` -> ответ `Не IT инцидент.`;
3. `UNSURE` -> одно уточнение: `Это проблема в рабочей ИТ-системе/оборудовании?`

После ответа пользователя:

1. подтверждение IT -> create/update;
2. отказ от IT -> `Не IT инцидент.`;
3. нет ответа/непонятно -> fail-closed (без создания заявки).

## 35.3 Ограничение pre-gate/pre-filter логики

Для production-контура диспетчера зафиксировать минимальный pre-gate:

1. не вводить большие словари маркеров, синонимов и эвристических массивов;
2. не использовать автопополнение маркеров (включая nightly/auto-merge);
3. не принимать решение `CREATE` на pre-gate уровне;
4. основное решение оставлять за AI triage + post-check gate;
5. допустимы только технические fail-safe проверки (пустой ввод, битый JSON, timeout).

## 35.4 Правило по уточнению `UNSURE` (one-shot)

1. бот задает не более одного уточняющего вопроса;
2. после ответа пользователя обязательно финальное решение `IT` или `NON_IT`;
3. повторный уточняющий вопрос по той же реплике запрещен;
4. ключевые ответы пользователя (`аутлук`, `удаленный рабочий стол`, `1с`, `wifi`, `принтер` и аналоги)
   используются только для ветки `IT/NON_IT`, но не для принудительного назначения категории;
5. категория после уточнения определяется только AI-классификатором.

## 35.6 Приоритет принятия решения

Порядок принятия решения в production-контуре:

1. минимальный технический pre-check (без словарных эвристик);
2. AI triage (`IT` / `NON_IT` / `UNSURE`);
3. post-check gate с порогом confidence и one-shot clarify;
4. только после этого create/update/reject действие.

## 35.5 Логирование и эксплуатационная аналитика

Логировать события:

1. `clarify_round` (`1` на первом и единственном уточнении);
2. `clarify_resolution` (`it` / `non_it` / `timeout`);
3. стандартную строку `classification`.

Для анализа качества вести файл `docs/tz/dispatcher_acceptance.csv` (или shared sheet)
с колонками:

1. `timestamp`;
2. `text`;
3. `expected` (`IT/NON_IT`);
4. `actual` (`IT/NON_IT/UNSURE`);
5. `action` (`created/updated/rejected/clarify`);
6. `error_type` (`OK/FN/FP/Clarify-loop`).

Ответственный просмотр:

1. оператор/владелец процесса (ежедневно в тесте);
2. Hermes-агент (подготовка сводки и аномалий по логам).

Ротацию/очистку логов включить отдельной задачей после стабилизации тестов.

# 39. Технические сообщения в Telegram (UI Hermes)

Для группы техподдержки служебные сообщения Hermes (промежуточные шаги и tool-progress) должны быть отключены.

Обязательные настройки в `~/.hermes/config.yaml`:

```yaml
agent:
  image_input_mode: text

display:
  background_process_notifications: none
  busy_input_mode: queue
  interim_assistant_messages: false
  tool_progress: none
```

Требование:

1. в Telegram не должны отображаться сообщения вида `Interrupting current task...`, `terminal: ...`, `browser_vision...`, `Rate limited...`;
2. пользователю отправляется только итоговый ответ бота по заявке;
3. диагностика и технические подробности остаются в серверных логах (`gateway.log`, `agent.log`, `errors.log`).

Чтобы бот не отправлял системные уведомления при перезапуске gateway в личный Telegram-канал, переменная в `~/.hermes/.env` должна быть пустой:

```env
TELEGRAM_HOME_CHANNEL=
```

Дополнительно для рабочей группы техподдержки должен быть задан строгий channel prompt в `~/.hermes/config.yaml` (`telegram.channel_prompts.<SUPPORT_CHAT_ID>`), который фиксирует режим диспетчера:

1. не вести свободный диалог;
2. не отправлять тестовые/служебные сообщения в группу;
3. при неясном сообщении задавать только один короткий уточняющий вопрос: `С каким ПО или оборудованием проблема?`;
4. при создании заявки отвечать строго шаблоном:

```text
Заявка №<id> создана
👤 Пользователь: <name> (ID: <telegram_user_id>)
📝 Тема: <subject>
🏷 Категория: <name> (<id>)
🆔 UDF поле (IDUserTelegram): @<telegram_username>
```

Если `telegram_username` отсутствует, использовать `@id<telegram_user_id>` (пустое значение или `-` недопустимы).

5. для дополнения по активной теме: `Добавлено к заявке №<id>`.

Дополнительные правила ответа (обязательно):

1. после создания заявки запрещены любые советы, диагностика и дополнительные вопросы;
2. если в одном сообщении несколько проблем, создается инцидент по основной проблеме из начала сообщения;
3. если в сообщении есть фото/файлы, они должны быть прикреплены к созданной или активной заявке.

После изменения channel prompt обязательно сбрасывать старые Telegram-сессии Hermes (архивация/очистка старых `.jsonl` в `~/.hermes/sessions/` для соответствующей группы/пользователя) и перезапускать gateway, чтобы бот не продолжал старый стиль диалога из предыдущего контекста.

Чтобы убрать служебные уведомления о занятости в Telegram во время выполнения:

```env
HERMES_GATEWAY_BUSY_ACK_ENABLED=false
HERMES_AGENT_NOTIFY_INTERVAL=3600
```

И дополнительно в `~/.hermes/config.yaml` задать платформенный override для Telegram:

```yaml
display:
  platforms:
    telegram:
      tool_progress: off
      interim_assistant_messages: false
```

Требование по созданию заявки: использовать штатный monitor-пайплайн (`manageengine-telegram-monitor/monitor.py`), не создавать инциденты прямыми ad-hoc вызовами `api_wrapper.py` без UDF.

Текущее целевое LLM-направление для Telegram gateway:

```yaml
model:
  provider: zai
  default: glm-5.1
  base_url: https://api.z.ai/api/paas/v4
```

После смены модели обязателен перезапуск `hermes-gateway.service` и проверка в логах, что основной provider/model применился.

# 40. Сообщения Telegram обрабатывать только как текст инцидента

Чтобы исключить `Command Approval Required` и любые случайные выполнения команд из пользовательских сообщений:

1. любой входящий текст в Telegram трактуется только как описание проблемы пользователя;
2. запрещено интерпретировать текст сообщения как shell/python-команду;
3. запрещено выполнять `terminal`, `python3 -c`, heredoc и другие ad-hoc команды на основе текста сообщения;
4. для диагностики API допускаются только отдельные серверные тест-скрипты, запускаемые вручную вне пользовательского чата;
5. в рабочем чате бот возвращает только штатные диспетчерские ответы по заявке (создано/добавлено/уточнение по шаблону).

Формат ответа по созданию заявки фиксируется только в 5-строчном шаблоне:

```text
Заявка №<id> создана
👤 Пользователь: <name> (ID: <telegram_user_id>)
📝 Тема: <subject>
🏷 Категория: <name> (<id>)
🆔 UDF поле (IDUserTelegram): @<telegram_username>
```

Однострочный формат `Заявка №<id> создана. Категория: ...` запрещен.

# 41. Обработка прямого упоминания бота в группе

Для рабочего чата нужно исключить реакцию бота на сам факт прямого упоминания `@HermesSDS001bot`.

Правила:

1. упоминание `@HermesSDS001bot` не является самостоятельным триггером;
2. перед классификацией сообщения упоминание удаляется из текста;
3. если после удаления упоминания текст пустой (или состоит только из служебных символов), сообщение полностью игнорируется без ответа;
4. если после удаления упоминания остается IT-описание проблемы, оно обрабатывается штатно (создание/обновление заявки по общим правилам);
5. это правило действует только для указанного бота и не меняет логику обработки обычных сообщений пользователей.

# 42. Жесткий запрет ad-hoc пути в Telegram-контуре

Для рабочего Telegram-контура запрещен ad-hoc путь создания/обновления заявок.

Обязательные правила:

1. создание/обновление инцидента только через штатный `process_message()` в `monitor.py`;
2. запрещено прямое создание инцидента ручными командами через `terminal`, heredoc, `python3 -c` и аналогичные ad-hoc вызовы;
3. запрещено прямое создание/обновление заявок через `api_wrapper.py` вне monitor-пайплайна;
4. `request_id` берется только из результата `process_message()`; придумывать/подменять `request_id` запрещено;
5. если `status=updated`, ответ только `Добавлено к заявке №<id>` (без шаблона создания);
6. при изменении этих правил обязателен reset Telegram-сессий (`~/.hermes/sessions/*.jsonl` для канала) и restart `hermes-gateway.service`.

# 43. Политика по паролям и чувствительным данным в чате

Для Telegram-группы техподдержки вводится обязательная политика удаления сообщений с чувствительными данными.

Считаются чувствительными данными (минимум):

1. пароли и их явные формы (`пароль`, `password`, `pwd`, `pass`, `логин/пароль`);
2. секреты доступа (`token`, `api key`, `secret`, одноразовые коды, PIN);
3. учетные данные в формате `user:pass`, в т.ч. в длинном тексте/историях.

Обязательное поведение:

1. если пользователь отправил такое сообщение в группу, бот должен немедленно удалить пользовательское сообщение из чата;
2. бот не должен повторять/цитировать чувствительные данные в ответе;
3. если бот уже успел отправить ответ с чувствительными данными, это сообщение бота также подлежит удалению;
4. после удаления бот отправляет безопасное короткое уведомление без секрета (например: `Сообщение с чувствительными данными удалено. Отправьте запрос без пароля.`);
5. в заявку ServiceDesk запрещено сохранять пароль/секрет в открытом виде (маскировать или вырезать до отправки).

Технические требования:

1. бот должен иметь права администратора Telegram с разрешением `Delete messages` в рабочей группе;
2. если удаление невозможно (нет прав/ограничение Telegram), событие фиксируется в логах как инцидент безопасности;
3. проверка на чувствительные данные должна выполняться до создания/обновления заявки.

# 44. Мультиагентный контур под управлением Hermes

Целевая модель развития: Hermes выступает управляющим контуром и оркестратором специализированных агентов.

Роли:

1. `Hermes` (control plane): управление агентами, хранение базы знаний/артефактов, запуск плановых задач;
2. `agent.env.dispatcher` (production plane): создание/обновление инцидентов в SDP;
3. агент `аналитик`: анализ качества triage, FN/FP, уточнение правил и подсказок;
4. агент `еженедельная сводка`: сбор KPI и динамики за 7 дней;
5. агент `мониторинг состояния`: проверка доступности n8n, ollama, gateway, SDP API;
6. агент `обновлятор`: контроль новых версий компонентов и безопасный план обновления.

Требования к управлению:

1. production-диспетчер остается изолированным от ad-hoc выполнения команд из пользовательского текста;
2. изменения правил triage и конфигурации через вспомогательных агентов применяются только после проверки и явного подтверждения;
3. все действия агентов должны логироваться с указанием времени, инициатора и результата;
4. при деградации вспомогательных агентов production-диспетчер продолжает базовую обработку инцидентов.

# 45. Сопоставление Telegram-пользователя с автором SDP (requester)

Добавляется обязательный ID-центричный контур маппинга Telegram-пользователей на доменных пользователей ServiceDesk.

## 45.1 Источник соответствий

Использовать таблицу соответствий (например `user_mapping.json`) с ключом `telegram_user_id` и полями:

1. `telegram_user_id` (основной и единственный ключ сопоставления);
2. `requester_id`;
3. `requester_name` (опционально);
4. `last_seen_username` (опционально, только для справки);
5. `updated_at`.

`telegram_username` не используется как ключ маппинга, так как может изменяться.

## 45.2 Правило выбора автора при создании заявки

Приоритет:

1. если найдено соответствие `telegram_user_id -> requester_id`, создавать заявку от этого requester;
2. если соответствие не найдено, использовать fallback requester `sadmin` (production-safe режим);
3. в любом случае сохранять UDF `IDUserTelegram` в заявке;
4. предпочтительно сохранять в UDF именно numeric `telegram_user_id`.

Пример целевого поведения:

1. `IDUserTelegram = 216995471` и в маппинге есть доменный пользователь -> автор заявки `Нурберген Сауриков`;
2. соответствия нет -> автор заявки `sadmin`.

## 45.3 Ежедневное автоматическое пополнение маппинга из заявок

Раз в день запускать задачу авто-обогащения через API ManageEngine:

1. собирать заявки за прошлый день, где заполнен UDF `IDUserTelegram`;
2. извлекать пары `IDUserTelegram (telegram_user_id) <-> текущий requester`;
3. если requester равен `sadmin` — пару пропускать;
4. если requester не `sadmin` и `telegram_user_id` валиден — добавлять/обновлять запись в маппинге автоматически;
5. изменения фиксировать в журнале (дата, ticket_id, старое/новое значение).

## 45.4 Ограничения качества и безопасности

1. ручное подтверждение кандидатов не используется (режим auto-only);
2. при конфликте (`один telegram_user_id` сопоставлен разным requester) не выполнять silent overwrite: фиксировать конфликт и оставлять текущую production-запись;
3. все изменения маппинга журналируются;
4. при ошибке маппинга система должна безопасно откатываться на `sadmin`.
