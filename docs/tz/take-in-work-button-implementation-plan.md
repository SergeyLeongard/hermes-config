# План реализации: кнопка "Принять в работу"

## Контекст

- Источник карточек: ops-группа `-1003568410359`, тема `3`.
- Цель: назначение `technician/group` в SDP из Telegram в 1 клик.
- Source of truth по назначению: ServiceDesk.
- Пилотный доступ: `@sergey_al5`, `@northmund95`.

## Этап 1. Контракт и конфиг

- Зафиксировать callback-data формат: `take:<request_id>`.
- Добавить enable-flag пилота и whitelist пользователей.
- Подготовить пилотный mapping `telegram_user_id -> technician_id + group_id`.

## Этап 2. Кнопка в карточке

- В карточку инцидента в Telegram добавить inline-кнопку `Принять в работу`.
- Сохранять связь `request_id <-> telegram_message_id` для последующего editMessage.
- Хранение state для MVP: локальный JSON (допустимо), далее можно перейти на SQLite.

## Этап 3. Обработчик нажатия

- Проверка прав нажимающего (whitelist пилота).
- Чтение текущего состояния заявки из SDP.
- Если уже назначено на другого: вернуть `already_taken`.
- Если свободно/пуловая: выполнить assign в последовательности `group_id -> technician_id`.
- После подтвержденного assign техника: проставить статус `В работе` (best-effort; не ломает успешное назначение при ошибке статуса).
- Вернуть callback-ответ пользователю и записать аудит-событие.

### Этап 3.1. Анти-рассинхрон SDP -> Telegram

- Периодически сверять карточки Telegram с фактическим состоянием в SDP.
- Если в SDP изменились `technician/group/status` - обновлять карточку в Telegram.
- Если в SDP назначение уже выполнено - снимать кнопку в Telegram и фиксировать ответственного.

### Этап 3.2. Take-in-work для email-origin заявок

- Для заявок, созданных из email, использовать тот же обработчик `Принять в работу`.
- После нажатия выполнять ту же последовательность `group -> technician -> status`.
- Логировать исходы по тем же кодам `result`, без отдельной ветки по источнику.

### Этап 3.3. Source-invariant lifecycle

- Источник заявки (Telegram или email) не меняет логику жизненного цикла после создания.
- Кнопочный контур назначения и правила синхронизации едины для всех источников.

## Этап 4. Обновление Telegram-карточки

- При `ok_assigned`: убрать кнопку, добавить строку `Ответственный: <ФИО>`.
- При `already_taken`: карточку не менять, показать callback с текущим ответственным.
- При ошибках: карточку не менять, кнопку оставить, вернуть короткий error callback.

## Этап 5. Гонки и идемпотентность

- Политика конкуренции: first-writer-wins.
- Повторное нажатие текущим владельцем: идемпотентный ответ `уже у вас в работе`.
- Повторное нажатие другим пользователем после assign: `already_taken`.

## Этап 6. Анти-рассинхрон SDP <-> Telegram

- Фоновый sync 1-2 минуты:
  - читать активные карточки с кнопкой;
  - если в SDP уже назначено, снимать кнопку и обновлять ответственного.
- Ограничить окно sync (например последние 24 часа).

Примечание: этап 6 реализует цели этапа `3.1` на уровне фонового контура.

## Этап 7. Наблюдаемость

- Аудит-лог минимум: `ts, request_id, tg_user_id, tg_username, technician_id, group_id, action, result, error_code`.
- Добавить KPI в orchestrator-контур:
  - `take_attempts_24h`
  - `take_success_24h`
  - `take_already_taken_24h`
  - `take_errors_24h`
- Вывод KPI в `orchestration_report`.
- Отправка KPI в Zabbix через `orchestrator_status -> zabbix_orchestrator_sync`.

## Этап 8. Тесты и rollout

- Тесты пилота:
  - успешное принятие (`@sergey_al5`);
  - второй клик другим пользователем -> `already_taken`;
  - пользователь без прав -> `forbidden_user`;
  - отсутствует mapping -> `mapping_not_found`;
  - назначение сделано в SDP вручную -> sync обновляет Telegram-карточку.
- Запуск пилота на 2 пользователях.
- После стабилизации: расширение прав на весь `it_staff.json`.

## Definition of Done

- Назначение из кнопки корректно обновляет SDP и карточку Telegram.
- Двойного назначения по гонке нет.
- Все ключевые исходы логируются с нормализованным `result/error_code`.
- KPI кнопки видны в отчете оркестрации и Zabbix.
